# Phantom Check ("No Ghost APIs")

## Rule
Do not call a function, method, or attribute -- or import a name -- unless you can point to it in the surface
you were actually given (the provided module/stub, the imports already present, the language's documented
builtins). A plausible-sounding name is not evidence that it exists.

## Procedure (verify the surface BEFORE you call)
1. List the real surface: what does the provided module/stub actually define? What is already imported?
2. For each symbol you intend to call, find it in that surface (or in builtins you are certain of). If you
   cannot, it is a phantom -- do not use it.
3. Match the exact name and signature shown; do not "improve" `to_cents` into `parse_money`, or assume a
   list has `.first()` / `.last()` because it would be convenient.
4. If the capability you want is genuinely absent, implement it from what exists rather than inventing it.

## Surface Report (required artifact -- paste BEFORE the diff)
- **Available surface:** <the real names from the provided module / stub / imports / builtins you will use>
- **Symbols I call:** <each one, mapped to where it is defined in the surface above>
- **Phantoms avoided:** <any tempting name you considered but could not confirm -- "none" is fine>
- **Decision:** use only confirmed symbols | implement the missing piece from what exists

## Guardrails
- An import or call that does not resolve is a hard failure (ImportError / AttributeError), not a style nit.
- Confidence is not confirmation -- "I'm pretty sure `str` has that method" is exactly how phantoms ship.
- When the provided surface is small, that is a constraint to design within, not a gap to paper over with
  invented helpers.
